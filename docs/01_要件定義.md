## 1. 背景・目的

### 背景

問い合わせ窓口に届くメールは、見積の依頼、不具合の報告、請求の確認などが混在している。担当者が1通ずつ読んで振り分け、要点を転記し、一次返信を書く作業に時間がかかり、急ぎの問い合わせが埋もれることがある。

### 目的

- 問い合わせメールを生成AI（LLM）で分類し、要点を決まった形（構造化データ）で取り出す
- 分類ごとに記録用の行と返信の下書きを作り、担当者の一次対応を短くする
- AI が失敗しても問い合わせを取りこぼさず、人の確認に回す

## 2. 機能要件

| ID | 要件 | 優先度 |
|---|---|---|
| REQ-001 | 問い合わせメール（差出人・件名・本文）を Webhook で受け付ける | 必須 |
| REQ-002 | LLM で問い合わせを「見積依頼／不具合報告／請求関連／その他」の4分類に分ける | 必須 |
| REQ-003 | 会社名・担当者名・用件の要約・緊急度（高／中／低）を JSON で取り出す | 必須 |
| REQ-004 | 分類ごとに担当窓口を決め、記録用の行データと返信の下書きを作る | 必須 |
| REQ-005 | 入力に不備（本文なし・件名なし・形式違い）がある場合は LLM を呼ばずにエラーとして返す | 必須 |
| REQ-006 | LLM の呼び出しが失敗した場合は再試行し、それでも失敗したら「要確認」として扱う | 必須 |
| REQ-007 | LLM の出力をスキーマで検証し、不正な場合は1回だけ再依頼し、それでも不正なら「要確認」として扱う | 必須 |
| REQ-008 | 失敗の内容（段階・理由・時刻）をエラーログとして残す | 必須 |
| REQ-009 | LLM の提供元（ローカル LLM・クラウド LLM）を設定の変更だけで差し替えられる | 推奨 |
| REQ-010 | トリガーを Gmail・IMAP の受信に差し替える手順を用意する | 推奨 |

## 3. 非機能要件

| 区分 | 要件 |
|---|---|
| 失敗時の扱い | どの段階で失敗しても、呼び出し元に結果（成功・要確認・入力エラー）を必ず返す。処理が途中で止まって無応答になる状態を作らない |
| 再試行 | LLM の通信に失敗した場合は、初回を含めて最大3回まで、間隔2秒で呼び出す。出力の形式不正は1回だけ再依頼する。1通あたりの LLM 呼び出しは最大6回（2回の依頼×各3回）に収まる |
| 個人情報の扱い | LLM に送るのは件名と本文だけとし、差出人のメールアドレスは送らない。エラーログに本文を残さない。n8n の実行データ（本文を含む）は、正常に終わった実行（成功・要確認・入力エラー）では保存しない。想定外の失敗で止まった実行は調査のため保存し、n8n の保存期間の設定で削除する。ローカル LLM を使う構成では外部へ送信しない |
| コスト | 出力の上限トークン数を設定する。分類と抽出は1回の依頼でまとめて行う。クラウド LLM に切り替える場合は小型のモデルで足りる設計とする |
| 保守性 | ノード名は英語で統一し、式から参照しやすくする。設定値（接続先・モデル名・再依頼回数）は1か所の設定ノードにまとめる |

## 4. 対象外

- 実際のメール送信（作るのは返信の下書きまで。送信は人が確認してから行う）
- 添付ファイルの読み取り
- 表計算シート・データベースへの書き込みの実装（書き込む行データまでを作り、接続方法は導入手順に記載する）
- 同じメールが二重に届いた場合の重複排除
- 多言語の問い合わせ（日本語を前提とする）
