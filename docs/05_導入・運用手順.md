## 1. 前提

| 項目 | 内容 |
|---|---|
| n8n | 2.3.5 で動作確認（セルフホスト・Docker） |
| LLM | OpenAI 互換の Chat Completions API を持つもの。動作確認は Ollama の qwen2.5:7b |
| ネットワーク | n8n から LLM の URL に到達できること。n8n を Docker で動かし、同じ PC の Ollama を使う場合は `host.docker.internal` で到達する（Docker Desktop の場合。Linux の Docker Engine では起動時に host-gateway の指定が必要） |

## 2. インポート

1. n8n の画面でワークフローの一覧を開き、新規ワークフローを作る
2. ワークフロー画面のメニューにあるファイルからの読み込みで `workflow/ai-mail-triage.json` を指定する（または JSON の中身をコピーしてキャンバスに貼り付ける）
3. 保存する

API で取り込む場合は、n8n の公開 API（`POST /api/v1/workflows`）に `name`・`nodes`・`connections`・`settings` を送る。

## 3. 設定値と資格情報

### 設定値（Set Config ノード）

| 項目 | 既定値 | 説明 |
|---|---|---|
| llm_base_url | `http://host.docker.internal:11434/v1` | LLM の API の URL（`/chat/completions` の手前まで） |
| llm_model | `qwen2.5:7b` | モデル名 |
| llm_max_tokens | 400 | 回答の上限トークン数 |
| max_schema_retries | 1 | 出力が不正だった場合の再依頼の回数 |
| max_body_chars | 20000 | 受け付ける本文の最大文字数 |

### LLM の差し替え

| 使う LLM | llm_base_url の例 | 資格情報 |
|---|---|---|
| Ollama（同じ PC・Docker の n8n から） | `http://host.docker.internal:11434/v1` | 不要 |
| OpenAI 互換のクラウドサービス | 各サービスの API の URL（末尾 `/v1` まで） | 必要 |

クラウドの LLM を使う場合は、Call LLM ノードの認証の設定で Header Auth 方式の資格情報を新規作成して選ぶ（名前は例として `LLM API`、ヘッダー名は `Authorization`、値は `Bearer ` に続けて API キー。ヘッダーの形式は各サービスの公式ドキュメントで確認する）。API キーをノードの URL や本文に直接書かない。各サービスの URL・モデル名・JSON モードへの対応は、各サービスの公式ドキュメントで確認する。

## 4. 動作確認

ワークフローを保存して有効化（Active）し、次のように POST する。

```bash
curl -s -X POST http://localhost:5678/webhook/inquiry-triage \
  -H 'Content-Type: application/json' \
  -d '{"from":"sample@example.com","subject":"お見積りのお願い","body":"在庫管理表の Web 化について概算のお見積りをお願いします。"}'
```

期待する結果: HTTP 200、`"status":"ok"`、`"category":"見積依頼"`。

テストケース一式は `tests/run_live.py` で実行できる（テスト仕様書を参照）。

## 5. トリガーの差し替え

ワークフローの後半は `from`・`subject`・`body` の3項目だけを使う。トリガーを差し替えたら、その直後に Edit Fields (Set) ノードを1つ置いて3項目に詰め替え、Validate Input が読む場所（`$('Receive Inquiry').first().json.body`）を差し替えたノードに合わせる。

### Gmail

1. Gmail Trigger ノードを追加し、Gmail の資格情報（OAuth2）を設定する。取得の間隔と対象（例: ラベル「問い合わせ」・未読のみ）を決める
2. 詰め替えノード（例: `Map Email Fields`）で次のように設定する（項目名は Gmail Trigger の出力を実際に確かめてから合わせる）
   - from: 差出人
   - subject: 件名
   - body: 本文（テキスト）
3. Validate Input の2行目を `const raw = $('Map Email Fields').first().json;` に変える
4. Respond Success・Respond Error は不要になるため、記録先（表計算シート等）のノードに置き換える

### IMAP

1. Email Trigger (IMAP) ノードを追加し、IMAP の資格情報を設定する
2. 以降は Gmail と同じ（差出人・件名・本文のテキストを3項目に詰め替える）

メールトリガーでは、同じメールを二度読む・読み落とすといった扱いがトリガーの設定（既読にする・対象のフォルダ）で変わる。本番に入れる前に、テスト用のメールボックスで確認する。

## 6. 記録先の接続

- 成功時: Build Record の後ろに表計算シート（Google Sheets の「行を追加」など）やデータテーブルのノードを置き、`response.record` の各項目を列に対応させる
- 失敗時: Log Error の後ろに同じく記録用のノード、またはチャットへの通知ノードを置き、`logEntry` を送る
- 返信下書き: `response.replyDraft` をメールの下書き作成ノードに渡す。送信は人が内容を確かめてから行う

## 7. 実行データの保存

n8n は既定で、実行ごとの入出力（メール本文・抽出結果を含む）をデータベースに保存する。本ワークフローはワークフローの設定で次のようにしている。

| 設定（ワークフローの設定） | 値 | 意味 |
|---|---|---|
| saveDataSuccessExecution | none | 正常に終わった実行（成功・要確認・入力エラーのいずれも）のデータを保存しない |
| saveDataErrorExecution | all | 想定外の失敗で止まった実行は、調査のため保存する（本文を含む） |

- 保存された実行は、n8n の保存期間の設定（環境変数 `EXECUTIONS_DATA_PRUNE`・`EXECUTIONS_DATA_MAX_AGE`・`EXECUTIONS_DATA_PRUNE_MAX_COUNT`）に従って削除される。n8n 2.3.5 の既定値は、削除が有効・336時間（14日）・最大10,000件。社内の規程に合わせて短くする
- 動作を調べるために一時的に成功時も保存する場合は、ワークフローの設定で保存を有効にし、調べ終わったら戻す
- 画面上の手動実行は別の設定（手動実行を保存するか）に従う。本番データで手動実行しない

## 8. 監視

| 対象 | 確認方法 | 頻度の目安 |
|---|---|---|
| 要確認の件数 | 記録先で status が「要確認」の行を数える。急に増えたら LLM の停止・応答形式の変化を疑う | 毎日 |
| エラーログ | Log Error の記録先（またはチャット通知）で stage ごとの件数を見る | 毎日 |
| 実行の失敗 | n8n の実行履歴で失敗した実行を確かめる（正常に終わった実行は保存されないため、要確認・入力エラーの件数は記録先で数える）。ワークフローの設定で「エラーワークフロー」を指定すると、想定外の失敗（ERR-004）も通知できる | 随時 |
| 応答時間 | 実行履歴の所要時間。LLM のモデルを変えた後は特に確認する | 変更時 |

## 9. 再実行

- 要確認になった問い合わせは、記録の件名・差出人から元のメールを探し、内容を人が確認して対応する
- LLM の停止が原因だった場合は、復旧後に同じ入力を Webhook に送り直せば再分類できる（重複排除はしていないため、記録先で元の要確認の行を整理する）
